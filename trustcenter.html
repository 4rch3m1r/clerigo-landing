What the product does

These are not intentions: it is what is written in the code and is checked on every change by the test suite. Every point here comes from a check against the repository.

Isolation between organisations

  • Isolation is enforced by the database, not just the code: every protected table compares the row's organisation with the session's.
  • Fails closed. If the code forgets to filter, nobody's data comes out: with no organisation set, the comparison matches no row.
  • The policy is enforced on the table owner as well, so not even the schema owner gets past it.
  • 136 tables with an isolation policy in the engine. The ones left out are listed one by one with their reason written down.
  • The application connects as a user that is not an administrator and cannot bypass the policies.

Encryption

  • The credential vault encrypts with AES-256-GCM, authenticated encryption: as well as hiding, it detects tampering.
  • Envelope encryption: a new, single-use key per secret, itself closed with the deployment key.
  • From the master key comes a different one per scope with HKDF-SHA256. A secret belonging to one organisation cannot be opened from another.
  • If the master key is missing, the vault refuses to save: it does not write in clear text as a fallback.
  • Passwords are not stored: what is stored is a bcrypt cost-12 digest.
  • Integration secrets are encrypted field by field before they touch the database.

Identity and access

  • Second factor with an authenticator app, standard RFC 6238. Any authenticator works.
  • A code cannot be used twice: the accepted time step is stored and the next attempt is rejected.
  • The race between two requests with the same code is settled by the database, not the application.
  • Passkeys with the private key encrypted and tied to the person.
  • Ten recovery codes, each single-use; generating new ones voids the previous ones.
  • Progressive lockout of the account, a brake against password spraying and a request limit per minute and per origin.

Audit trail

  • Each entry is chained to the previous one by a SHA-256 hash: altering one breaks the chain of every entry that comes after.
  • When the chain is checked, it recalculates the hash from the stored columns, hashes are not compared with each other.
  • The application cannot modify or delete entries: its database roles can only read and append.
  • There is no call in the code that modifies, deletes or prunes them by age.
  • Removing an entry from the middle or changing its content is flagged, with the exact entry where it breaks.
  • The platform console keeps its own log, outside the organisation, so that the entry outlives the removal of that organisation.

Network and browser

  • Five security headers on every response: HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy and Permissions-Policy.
  • Content policy (CSP) regenerated on every request, with a single-use number for the scripts.
  • The caller's address is read in a way that cannot be forged: it is counted from the end of the header and the number of intermediaries is declared.
  • Rate limiter on the public doors: sign-in, password recovery and organisation registration.

Operations on your data

  • A maintenance operation on an organisation requires a second factor, permission checked against the database and a written reason. In that order.
  • No one can grant themselves permission to operate the platform: it must be granted by someone else.
  • An entry is recorded before the operation and another after, with whom, when and why.
  • The second factor code never travels on the command line: it is asked for at the console so it does not stay in the history.

Personal details

Clèrigo processes personal data on behalf of your organisation, which remains the controller. The product ships with the tools to comply, and they are the same ones Clèrigo uses internally.

Data subject rights

  • Access, rectification, erasure, portability, objection and restriction, each with its own file.
  • The deadline is counted against the date every time it is checked, not against a number saved on the day it was created: a request past its deadline shows as past its deadline.

Gaps

  • When a breach is registered, the platform calculates the 72-hour deadline from the declared detection time.
  • The file records what happened, who it affected and what was done.

Framework

  • Catalogue of 77 privacy controls from four frameworks: ISO 27701, GDPR, Law 172-13 and NIST Privacy Framework.
  • The Dominican Law 172-13 and the GDPR are inside the catalogue, article by article and explained in plain language.
